# 产品愿景

## 一句话

Upstream Radar 持续监控 DSH 插件及其全部依赖；漏洞、恶意包或可能不兼容的升级出现后，它准确找到受影响的项目，再由同一个 DSH 运行时里的 Agent 阅读项目代码并产出可执行结论。

## 用户真正购买的结果

用户不需要另一份“发现 12 个高危漏洞”的报告。他需要知道：

1. 哪个正在使用的插件受到影响；
2. 问题藏在哪一层依赖；
3. 哪些项目实际使用了这个插件；
4. 漏洞触发条件在项目中是否成立；
5. 应该升级哪个插件版本，而不是一个自己无法控制的间接依赖；
6. 安全修复或 DSH 升级会不会顺手把项目弄坏；
7. 这件事应该通知谁。

## 两类持续变化

### 安全变化

- 新漏洞第一次命中当前版本；
- 某个包被确认是恶意包；
- 漏洞说明、危险程度或受影响范围发生重要更新；
- 原来没有修复版本，现在出现了修复版本；
- 公告被撤回，或者项目升级后不再受影响。

### 兼容性变化

- 插件发布了跨兼容边界的新版本；
- DSH 预览版发生升级，插件声明的兼容范围不再覆盖；
- 插件入口、exports 或 bundle 配置变化；
- Node.js 要求超过项目当前环境；
- 发布者明确说明存在 breaking change；
- 一个安全修复版本虽然消除了漏洞，却需要迁移 API 或配置。

两类变化共用同一张依赖图、项目清单、负责人和通知通道。

## 程序和模型如何分工

程序负责不能猜的事实：

```text
parser@2.9.0 是否受到该公告影响
它通过 plugin → logger → parser 进入项目
项目当前运行 Node.js 22
候选插件要求 Node.js >=24
插件声明的 DSH 范围是否包含候选版本
```

DSH Agent 负责必须结合项目才能回答的问题：

```text
漏洞功能是否真的被调用
外部输入能否到达危险代码
升级改变了哪些 API 和配置
最低成本的修复和迁移方案是什么
需要马上停用、24 小时内升级，还是继续观察
```

模型不是漏洞数据库，也不是版本比较器。

## 为什么必须做成 DSH 原生插件

DSH 采用 Everything is a Plugin 的组合方式。Radar 本身应该成为 profile 中的一层：和 Agent 共用 Cordis 生命周期、Session、项目目录与权限边界，而不是从飞书或另一个远程入口遥控电脑。

```text
DSH 安装插件
  -> Radar 保存插件依赖图
  -> Radar 长期监听上游变化
  -> 命中后生成一个受约束任务
  -> 通过 ctx.agents 向在线 DSH Agent 发送 plugin notice
  -> DSH Agent 在项目上下文和只读权限中调查
  -> 结果回到项目负责人
```

检测核心仍然保持确定性，task 也可以导出为文本或 JSON 以便调试；但当前产品只对 DSH 原生闭环负责，CLI 不是另一条产品集成路线。

这不是给漏洞条目加一段 AI 摘要，而是让 Agent 带着真实项目上下文处理一个已经确认命中的事件。

## 信任边界

- 公告和发布说明都是不可信数据，不能成为模型指令；
- 版本命中必须由程序计算；
- breaking signal 不等于确认不兼容；
- 模型结论必须附项目证据并标明置信度；
- 首版只读分析，不自动修改项目；
- 事件先持久化，再唤醒模型，避免 DSH 重启时丢警报；
- 不变的事件不重复通知。

## 产品演进

第一阶段完成“发现 → 精确路径 → DSH 原生投递 → Agent 分析”，并用真实 DSH headless profile 验证 bundle、Session 和 follow-up 链路。

第二阶段接入飞书、Slack 和项目会话，让结论抵达负责人并被确认。

第三阶段增加 GitHub Action：在 Pull Request 中重算依赖图、验证升级、运行兼容性测试。

第四阶段才在人工批准后创建修复分支或 Pull Request。

## 不做什么

- 不评价插件是否好用；那需要 benchmark；
- 不把所有新版本都叫 breaking change；
- 不让模型凭一篇新闻猜哪些项目受影响；
- 不以一个总分代替依赖路径和项目证据；
- 不在没有验证的情况下宣称升级已经修复全部路径；
- 当前不自动开 Issue、改代码、提交 PR 或合并。
