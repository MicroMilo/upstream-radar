# 产品愿景

## 一句话

Plugin Notary 在插件进入 Agent 之前，对精确版本进行独立的供应链审查，并签发可验证的安装凭证。

我们不评价插件“好不好用”。效果、任务成功率、工具选择和成本属于 benchmark。我们只回答：

1. 用户将要安装的是否真是它声称的那个产物；
2. 源码、构建、发布和依赖链是否能够追溯；
3. 安装过程是否包含危险或无法解释的行为；
4. 新版本相对已审版本是否出现供应链异常；
5. 证据是否满足个人或组织的安装策略。

## 为什么从 DSH 开始

DSH 的插件安装入口直接连接包管理器，插件可以通过 npm、Git、路径或 tarball 进入 profile。Git 插件还可能在安装期间执行 `prepare`。这使 `dsh plugin add/update` 成为清晰而有价值的准入边界。

DSH 是切入口，不是产品边界。核心证据模型应能逐步覆盖 MCP server、skills、Claude Code/Codex 插件以及其他 Agent 扩展格式。

## 产品形态

### 本地执行器

- 在隔离区解析依赖并获取候选产物；
- 绝不在用户宿主机上执行未知安装脚本；
- 验证下载内容、审查凭证和组织策略；
- 确保安装内容与审查内容具有相同摘要；
- 启动 DSH 前重新验证已安装内容。

### 公共审查服务

- 主动收录和持续监测公开插件；
- 保存每个版本的来源、构建、依赖和风险变化；
- 为同一摘要复用审查结果；
- 公开方法、覆盖范围、发现和撤销记录；
- 对高风险或自动检查无法覆盖的插件进行人工 review。

### 企业准入

- 私有插件和私有依赖扫描；
- policy-as-code；
- CI、开发机和运行环境统一执行；
- 签名凭证、例外审批、有效期和撤销；
- 审计证据与内部资产清单。

## 我们不做什么

- 不通过星标、下载量或作者声誉宣称安全；
- 不把 provenance 当作“没有恶意代码”的证明；
- 不把缺少发现描述成通过；
- 不给作者或仓库永久认证；
- 不以一个不可解释的总分掩盖证据；
- 不把插件效果 benchmark 混入供应链结论。

## 核心飞轮

```text
插件安装请求
  -> 查询精确摘要的审查凭证
  -> 未知或变化产物进入扫描/review
  -> 形成公开版本档案
  -> 作者主动补充 provenance 与可复现构建
  -> 更多安装可以快速验证
  -> 异常更新更容易被发现
```

最终目标不是成为另一个插件排行榜，而是成为 Agent 扩展生态的独立供应链信任层。
