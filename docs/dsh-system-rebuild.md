# DSH 兼容性系统重建与验收

目标：根据仓库证据推理作者实际环境，持续验证一批插件在作者基线和目标 DSH 环境中的兼容性，并留下可恢复、可复核的完整链路。

## 必须满足的行为

- 仓库审阅保存有来源的 Node、包管理器、overrides、profile / adapter 要求；区分作者推荐、CI 配置、声明支持与实际测试。
- 计划准确表达作者默认使用方式和新宿主测试环境。无法执行的环境明确留下覆盖缺口。
- 目标代码只在隔离执行器运行；依赖、配置、加载、运行检查具有明确结果和独立的环境依赖图。
- 宿主、浏览器及其他客户端证据正确归属。声明不满足、运行失败、基础设施失败、未知不能互相替代。
- 精确安装包、依赖图、执行环境和收集器版本决定证据复用。新事实触发重查，未变化的事件不重复发送。
- 审阅与执行任务先持久化再交付；中断可恢复，重试有界且公平。
- 用真实插件批次从最新版本观察、自动仓库审阅、计划、隔离执行直到统一汇总完成一次运行，再验证未变化、输入变化和失败恢复。

## Agent 主导的最小闭环

这不是“脚本失败后再叫模型来解释”。每个插件有一个从审阅开始就工作的 Agent：先读取有来源的仓库证据，提出 Node、包管理器和作者实际使用的 profile / adapter；可信程序校验并保存决定；Agent 再启动隔离执行，持续读取每个运行阶段的在线心跳、任务状态和结果。一个阶段停滞或失败时，Agent 在同一任务中检查、区分环境和插件原因，必要时选择操作员预设的网络路线、调整有证据的环境建议、重试，并一直跟踪到可执行组合收敛或留下明确覆盖缺口。

本机已有 ChatGPT 登录时，也可让 Codex CLI 经单一受限 MCP 手段自动批准这些命名 broker 动作，主机 shell、补丁与文件写入都被禁用；不把登录凭证复制或挂载进目标容器。这条路径同样不逐步等待人工审批，但不在宿主上开放无限制 YOLO 权限。

真实 Context 案例显示 15 秒唤醒间隔在较慢模型回合下使在线观察间距接近 45 秒验收门槛；后续本机和隔离容器 Agent 已缩短为 8 秒。前文的 15 秒是原设计值，不再是新启动案例的调度配置。

Agent 的“手脚”是命名的 `review`、`recommend`、`network`、`launch`、`watch`、`inspect`、`cancel`、`build-review`、`build`、`surface-build-review`、`surface-build`、`conclude` 操作，不是主机 shell。它不能自行指定代理、registry、版本或目标容器；只能作用于自己的插件。目标代码继续在无模型凭证、无主机挂载的只读执行容器里运行。YOLO 只用于一次性 Agent 容器；该容器无直接公网路线，经无凭证的受控出口仅连接模型服务。所有源文件、日志和报告在 Agent 边界都是不可信资料，心跳不是兼容性判决。`watch` 提供当前命令多久没有新增输出的有界提示，但 worker stderr 不能证明插件或网络故障；`inspect` 必须另用 Docker 精确任务句柄核实容器状态，核实失败要重试，不能直接取消或归因。可信 broker 保存精确本轮编号的在线监测时间：实际执行期间从启动、每次在线 `watch` 到结束，间隔不得超过 45 秒；只在完成后读取汇总不算主动监测。调度器每 8 秒唤醒同一模型会话，单次模型工作最多 30 秒，超时立即续接而不再等待一轮。依赖构建门槛必须由当前隔离报告明确列出；两类 `build-review` 都在模型判断前保存分析任务，两个 `build` 动作只允许当前观察过的包。原生批准绑在精确插件包、执行环境和运行依赖图上；Web/TUI 批准还绑在它自身的依赖图上。插件尚未装完时允许使用当前 profile 锁文件解析出的精确依赖图，装好后优先用已安装图；没有任一可验证图时留下覆盖缺口，不能套用旧批准。每轮最终还要 `conclude` 保存对精确运行报告和账本摘要的模型归因回执；它明确不是兼容通过证明，没有回执不算 Agent 闭环。

Agent 另有 `evidence` 手段：小文件按仓库相对路径补读；超出单文件采集上限的 README 可指定有界字节 `offset`，从同一仓库精确提交版本读取最多 24 KiB 的 UTF-8 片段。可信 broker 只接受固定仓库／提交／相对路径，不接受任意 URL 或命令；有源读取凭证时使用 GitHub contents API，并要求普通文件类型、精确大小和 Git blob 摘要相符。源文件最多 256 KiB，审阅总文本仍最多 192 KiB；首轮收满 24 文件也保留最多 8 个补读名额。新增片段成为独立的指纹化证据，先持久化待审任务，并使旧推理、旧执行和旧回执失效；Agent 必须重新 `review`、`recommend`、`launch` 才能结案。源读取凭证仅留在可信 broker，不传给模型或目标插件执行器。

MVP 验收首先看真实行为，而不是只看我们自己写的局部测试：从当时最新的精确 DSH／插件版本开始，让同一 Agent 对一批插件独立完成审阅、环境推理、依赖安装、注册／加载、作者预期 profile 或 adapter 的运行检查、在线介入、失败归因和二次运行的证据复用。单元测试只保护安全边界与已发现的回归。没有模型参与的人工建议批次不能算 Agent MVP 验收。

新算法以更高精度、更低模型开销推理 Node/profile，是闭环稳定后的下一阶段，不是 MVP 门槛。公开 issue／PR 也只在确定是上游缺陷、已有覆盖缺口和可复现证据后另行决定。

## 当前可证明的进度（2026-09-16）

- 本地已写好 `dsh-active-agent-mvp.yml` 的八插件 × DSH `next`/`alpha` 两条独立发布渠道编排（16 个隔离任务）。它仍未提交到远端，不能声称已可从 GitHub 手动触发；仓库 Actions 当前也没有 `CODEX_ACCESS_TOKEN` 或 `CODEX_API_KEY` Secret。远端凭证化模型批次尚未运行，但本机已有 ChatGPT 登录的受限 MCP Agent 路径已经实测，不能再把本机和 CI 混为一个阻塞。
- 主动 Agent 已从单次模型调用改为同一会话的定时续接；broker 对每一轮记录在线读取时间和归因回执，不能用一条最终回答或一次早期 `watch` 冒充完成。Web/TUI 仅出现于作者 profile 的构建门槛现在有独立的持久任务和有界批准，跨进程 broker 测试已覆盖安装前 profile 锁文件依赖图。旧构建批准在图变化后不会直接进入新一轮。
- 在线 `watch` 已补充当前命令的心跳年龄和无输出时长；`inspect` 现在会核实本插件真正运行的 Docker 容器，而不是只展示旧账本。无凭证、无目标代码的真实隔离容器已验证该精确状态检查，测试容器随后自动移除。这些信号为模型介入提供观察材料，不替代模型实际诊断。
- 执行计划现在保留本轮仓库推理输入的精确指纹；broker 的 `conclude`、调度器关闭判断和 CI 验收均要求汇总建议仍来自当前输入。新增仓库证据后误用旧结论的漏洞已用先红后绿的测试和跨进程 broker 测试复现并修正。
- 若批次已经完成且没有遗留运行任务，退出码 2 只有在计划明确列出无法执行的作者环境时才可作为覆盖缺口结案；运行器故障、未完成任务或无理由的非零退出仍不能结案，也不算兼容通过。
- Agent 关闭当前插件后，流水线另起同输入的确定性第二轮批次，要求执行 0 个任务、执行器身份和兼容账本的字节摘要均不变；这一步不调用模型、不使用模型凭证。`v12` 四插件 × 两渠道的八例当时确实逐个复跑 0 项，但旧人工复跑误写回原批次目录，覆盖了和模型回执绑定的汇总；这些旧目录现在不再满足完整结案校验，不能冒充现存的可复核闭环。通用批次运行器现会拒绝覆盖已有 Agent 回执的目录，同输入复跑只在独立目录进行。旧八例按固定源码快照从新隔离目录重建 `v13` 证据；跨渠道输入变化另用同一源码和执行器对 TUI 做真实验证，不拿同输入复用冒充变化覆盖。
- 全套本地测试通过（682 项；672 通过、10 跳过、0 失败）；飞书作者 legacy headless adapter 的执行计划、初始化观察、最终覆盖判断和执行器身份绑定均经过先失败再修复的回归检查。真实批次另暴露并修复了“精确 npm 制品下载失败的 `unknown` 报告被摘要门槛误拒收”、代理下载失败时 Agent 过早结案、模型传输连续失败仍无限巡检、以及 headless 实际依赖图并无独立 `dsh-lark-headless` 目录这四处系统缺陷。单元测试只守护边界，不能代替真实模型长期运行验收。同一 Codex 会话的跨轮续接已在本机登录加受限 MCP 的真实插件批次中运行；隔离 Agent 容器内的 30 秒中断续接仍未凭证化实测。
- 本地隔离边界已实测：Agent 网络无直接公网出口；受控出口允许模型服务、拒绝无关域名。代理侧车和临时测试网络已清理。
- 一次性 Agent 镜像补上了系统 CA 证书包：假 API key 冒烟测试能通过受控出口抵达模型服务，得到预期的 WebSocket/HTTPS `401`，而不是 TLS 验证失败。启动前还会验证 Docker daemon 能将精确控制目录以映射后的非 root 用户权限挂入，不能挂入时提前清晰报错，不会开始凭证化运行。本机这个独立 Colima profile 不共享 `/tmp` 或仓库目录，因此完整本地 Agent/broker 交互仍需原生 Docker 或显式共享挂载。

`dsh-environment/v13` 修正了一个真实跨渠道分类错误：OpenPencil README 的内部 headless exporter 曾在 `next` 被模型当作 DSH headless 作者工作流，而 `alpha` 没有。新规则要求明确的 DSH headless 操作、profile、模式或运行命令证据，不把插件内部组件名称当执行环境。OpenPencil 两渠道经同一 Agent 会话重新审阅为 Node 24／Web，分别实际执行 4 项并保存精确归因；两套 Web 检查兼容，目标原生因依赖图缺口保持 `unknown`，作者 DSH 基线的 `react-dom` peer 声明不兼容但不是运行崩溃。agy-link 两渠道重新审阅为 Node 24／作者 Web，原生安装加载和 Web 宿主各一项兼容；完整外部 CLI／Google OAuth 仍是覆盖缺口。这些 `v13` 观察是精确历史证据，不能覆盖升级后的审阅规则或执行器源码身份。

飞书仓库在英文/中文 README 明确写出默认 `sdk`、可切换到 `acp`、legacy `headless` 和 `web`。真实 `v13 next` Agent 只选 Web/SDK/ACP，`alpha` Agent 一度只选 Web，却把其余方式写作覆盖缺口；原门槛竟接受这两种缩小计划。`dsh-environment/v14` 新增一条最小的、插件自有文档正面声明完整性约束：对明确的默认/可切换 adapter 逐项要求执行 profile 和原文引述的作者工作流；内部 headless exporter 和仅属 DSH 平台的文档都不会触发。两渠道的模型会话已给出 Node 22 及完整 `headless/web/sdk/acp` 计划。作者 legacy headless adapter 现在有精确版本限定的独立 `doctor` 初始化 recipe；真实直连隔离批次已经执行目标与作者基线四个 headless 单元，CLI 初始化均返回 0，但旧 `v1alpha3` 图采集器误读不存在的 `dsh-lark-headless` 目录，四份回执保持 `unknown`。`v1alpha4` 改为按作者 CLI 实际使用的共同安装图核验精确 DSH headless 服务、file 制品与 peer；只读重验旧报告证明图中服务与版本存在，但旧回执不会被追认。两渠道已对实际 `protobufjs` 构建门槛逐条审阅、按精确制品及依赖图批准并发起新版隔离重跑；在新版 headless、Web、SDK/ACP 结果和同输入独立重播齐备前，不能宣称四种作者方式或 16 例完成当前系统验收。

`better-sidebar` 的真实规则升级曾因 README 补读片段绑定旧 `v12` 指纹而在 broker 启动时被拒绝。现在仅当重新计算的旧指纹与当前完整基础材料完全一致时，才把精确提交版本的补读片段重新绑定到 `v13`；插件制品、DSH 版本、基础文件或提交任何变化仍拒绝迁移。旧补读状态与新指纹的迁移回执另存，真实 `better-sidebar next` broker 已用这条路径建立新的待审任务。已结案的真实 Cloudflare `v13` 目录另做过直接写回检查：运行器拒绝覆盖，其汇总和 Agent 归因文件前后 SHA-256 未变。

修复扫描器源码使此前已结案的历史案例执行器身份不再代表当前源码。受信 host 的同会话源码身份重播入口只接受精确结案、同源建议且无待审任务；旧回执归档后，原 Agent 必须新 `launch`、健康阶段 `watch`、终态完整 `inspect/conclude`，确定性执行器按当前源码和依赖图决定需重跑的格子。Cloudflare `next` 已在直连路线新身份下完成 Node 20/22 × 原生/Web 四格：Node 20 原生安装未注册及 Web 表面均失败，Node 22 原生/Web 兼容；`alpha` 和 Context 的新身份重跑仍在进行。其余历史身份案例需逐个重审或重播，不能把旧身份的结果写成当前身份的复用验收。

### 迭代过程记录（旧观察与修复过程，不代表当前终态）

- Cloudflare 的人工建议对照批次在 DSH `0.1.5-rc.2` 上执行了 Node 20/22 × headless/Web 四个组合。Node 20 两个组合都因 DSH 未注册插件而失败，Node 22 两个组合可注册并加载，Web 宿主启动并挂载应用。执行时 profile 初始化出现持续心跳，最终报告与单独阶段能区分“命令成功”和“真正能用”。
- 2026-09-14 的人工建议对照批次没有模型主动推理，不能替代本轮验收。隔离 Agent 容器仍没有可安全传入的 Codex token/API key，本机独立 Colima profile 也没有通过控制目录挂载前检；本机真实八案例均改用现有 ChatGPT 登录的 Codex CLI、只读沙箱、禁用 shell/补丁和单一受限 MCP 手段。远端凭证化容器仍未实测。
- 2026-09-16 精确观察快照：npm `next` 的 DSH 是 `0.1.5-rc.2`，`alpha` 是 `0.1.6-alpha.1`，`latest` 标签当时为 `0.1.5-rc.1`；源码清单是 `0.1.6-alpha.1`。因此“最新”不能混同于 `latest` 标签，也不能只扫描 `next`。插件制品分别为 Cloudflare `0.1.9`、Context `0.52.2`、TUI `0.10.1`、飞书 `0.19.16`。第一次本地观察的飞书请求超时，启用本机已批准的环境代理后单目标重试成功。两个渠道均重新收集仓库证据并完成八个模型闭环；依赖图未完整解析的目标仍保持不完整覆盖。
- 每次 Agent `launch` 现在带独立编号；在线事件、最终汇总与 CI 验收只承认同一编号。用不存在的 Docker context 做故障注入后，broker 正确报告本轮失败和有界的、不可信故障提示，没有把上一轮 Cloudflare 汇总误报为完成。随后有效 context 的 Cloudflare 对照重跑收集了 Node 20/22 × headless/Web 四个组合：本轮编号与汇总匹配、4 个任务完成、0 个待执行、0 个执行任务失败；再次运行同一输入时执行 0 个任务并产生本轮独立汇总，证明精确证据复用。该对照仍采用人工审阅建议，不能代替四插件模型验收。
- `alpha` 的隔离诊断覆盖了四个插件，但未使用 Agent 推荐，也还不是作者 profile 验收：Cloudflare 在 Node 22 安装、注册、加载，因旧 `@deepseek-ai/dsh-tools@^0.1.5-rc.2` 留下 `@deepseek-ai/dsh-code-runtime@^0.1.5-rc.2` 未解析 peer，结果为 `unknown`；Context `0.52.2` 和 TUI `0.10.1` 在 Node 22 的临时 headless profile 都安装、注册、加载，但 Web 和作者命名 TUI profile 尚未测。Cloudflare 的 Node 20 DSH 初始化下载 `@types/node@26.6.0` tarball 收到 HTTP 404；npm 元数据声明该精确版本，相邻 `26.5.0` 可下载，所以不能归罪插件。
- 飞书 `0.19.16` 在 Node 22 的 `alpha` 诊断首次因 `protobufjs` 构建批准门槛停止；仅批准报告实际列出的 `protobufjs` 后，安装和注册通过，但加载进入需要真人飞书账号的二维码授权并超时，结论仍是覆盖不完整的 `unknown`。此门槛报告同时含精确插件包摘要和运行依赖图摘要，正是主动 Agent 新增受限构建动作的依据。新版收集器把一次性登录码、授权 URL 和二维码内容从交给 Agent 的阶段详情中隐去，保留“需要外部授权”原因。没有真人授权不能证明默认 SDK 用法已完成。
- 2026-09-16 的新鲜 `next` 仓库输入上，本机已完成首个真实 Cloudflare 主动 Agent 案例：模型从当前仓库证据建议 Node 22 优先、Node 20 为声明支持、作者 Web profile；随后独立执行 Node 20/22 × 原生/Web 四个任务。Node 22 两个组合安装、注册和加载成功，Web 宿主启动并挂载应用；Node 20 两个组合在 DSH 插件包注册处失败，不是下载、构建、网络或登录故障。Agent 在健康运行时也反复 `watch`，执行期在线观察最大间隔小于 45 秒，最终保存针对精确账本的归因回执。同一输入的确定性第二轮执行 0 个任务，执行器身份及三份账本不变。这个案例证明首个插件的主动监测和证据复用，不代表整批及 `alpha` 已完成。
- 首个真实案例暴露了我们自己的交互缺陷：MCP 把 `conclude` 的输入描述得过于宽泛，Agent 多次猜错字段，白耗了几轮。现已在受限 MCP 手段和模型提示中固定三个精确字段 `launchId`、`statement`、`coverageNotes`，错误输入在抵达 broker 前就得到明确反馈。下一插件正在按修正后的接口运行，以真实批次继续找系统缺陷。
- Context 的真实 Agent 案例揭出前置输入缺口：broker 虽接受仓库建议，却未把精确 `observations.json` 写进隔离执行器读取的审阅目录，导致两次 launch 在创建任务前失败。现已在 Agent 工作前有界地写入或核对输入，不一致的旧目录直接拒绝；同一模型会话使用可信修复提示重启。第一轮 16 个组合中，8 个 Node 22/24 原生兼容、作者 Web 6 个兼容、2 个旧 DSH Web 宿主因 `fs-ext@2.1.1` 构建留下环境缺口。broker 又错把作者历史 DSH 基线排除在构建审阅外；修复后，同一模型会话只对两条独立证据中的 `fs-ext@2.1.1` 批准宿主构建，第二轮 18 个真实组合全部兼容。执行期在线观察最大间隔 35.242 秒；同输入再执行 0 项，执行器身份及三份账本不变。旧保守结论与状态已归档，可恢复审计。
- TUI 的真实 Agent 案例从仓库证据推理 Node 24 为 CI 配置优先、Node 22 为声明支持，作者主要使用命名 `dsh-tui` 的 TUI profile。Node 22/24 的 4 个原生与 4 个 TUI 组合全部兼容；TUI 均显示真实 PTY 画面、接收输入并受控关闭，在线观察最大间隔 37.5 秒，模型保存精确归因回执。扫描器源码变化改变执行器身份后，旧状态未被错当同输入缓存；新身份重扫 8 项，随后同输入再执行 0 项，三份账本和执行器身份不变。
- 飞书 `next` 的真实 Agent 案例从作者材料选出 Node 22（CI 配置与最低要求，不冒称首选版本）、命名 `dsh-lark` profile、默认 SDK 和附加 ACP/Web/headless 流程。Agent 在健康运行时持续巡检，针对两条独立观察到的构建门槛，只批准仓库允许的 `protobufjs`，按准确制品与依赖图重跑。当前与作者基线的原生加载及 ACP 初始化均通过；SDK 在作者 `0.1.0-rc.8` 基线通过，在 `next 0.1.5-rc.2` 的 DSH host 依赖导出错误处失败；Web 在两套版本分别被 DSH host 导出错误和缺少 client entry 阻断，不是飞书账号缺失。限定启动环境对照也实际执行，但不证明真实消息收发。最终执行期在线观察最大间隔 29.154 秒；同输入再执行 0 项，执行器身份及三份账本不变。
- `alpha` Context 从独立仓库材料选择 Node 24 的 CI 配置优先、Node 22 的声明支持以及作者 Web；8 个原生与 8 个 Web 单元都有真实结果。两个旧 DSH Web 宿主的 `fs-ext@2.1.1` 本地模块门槛经 Agent 单独审阅、限量批准及重跑后解除；最终原生 8／8、Web 8／8 兼容，在线观察最大间隔 31.684 秒，同输入重跑 0 项。旧复用表面账本虽深度语义相等，一个字段的 JSON 对象键顺序却变化，导致回执字节摘要变化；现已稳定合并输出的字段顺序，并用回归测试固定，旧归档证据保持原样。
- `alpha` TUI 的第一次 Agent 回执误把 worker `task=accepted` 当成兼容结果，错误写成“全部通过”。精确账本其实是原生 4／4 兼容，作者 DSH 基线 TUI 2／2 兼容，`alpha` 目标 DSH 的 Node 22／24 TUI 2／2 `surface-incompatible`：真实 PTY 画面和交互出现，但受控关闭输入后没有停止。旧回执已归档，同一模型会话经终态完整 `inspect` 后准确重写结论；broker 现要求结案前检查精确 native/surface/adapter 账本，并拒绝与非兼容结果明显矛盾的整体通过表述。跨进程回归用例守护这个门槛。版本变化旧状态重扫再次观察到目标 TUI 关闭失败，不是单次模型文字判断。
- `alpha` 飞书首次执行暴露同一个系统误判：两个原生任务虽被执行器收下，报告却都是 `build-approval-required`，Agent 旧回执错误写“没有构建问题”。旧回执已归档；broker 现在禁止确切构建门槛未经依赖图绑定的 `build-review/build` 决定时结案。新 `v12` 仓库输入下，同一 Agent 对作者基线和目标 DSH 两条不同依赖图的 `protobufjs` 逐条审阅和批准，完成 12 个原生、Web、ACP、SDK 组合；作者基线 SDK 初始化兼容，目标 `alpha` SDK 初始化失败，Web 仍有宿主表面不兼容和外部账号覆盖缺口，不把启动当成真实消息收发。
- 长审阅结果曾使 Agent 重复请求已收集文件而收到“重复补读”错误。受限 `evidence` 动作现可精确重读已在当前有界输入中的文件，不改变输入指纹或创建新任务；真正新增的文件仍会使旧建议失效。这是让模型在材料截断时实际拥有可用取证手段的交互修正。

### `dsh-environment/v12` 八案例终态

四个插件各在 `next` 和 `alpha` 独立收集仓库材料；同一 Agent 会话主动巡检、必要时只批准当前依赖图中的宿主构建、终态完整读取原生／表面／adapter 三份账本，再按精确 DSH 版本保存归因回执。所有八例都在新执行器身份下实跑并同输入再跑 0 项，执行器身份和三份账本字节摘要不变。真实改变输入的对照另把 TUI 旧 `next` 状态带入 `alpha`：同一执行器只重跑 4 个目标组合，四个作者 DSH 基线账本条目逐字节不变；目标两条 TUI 受控关闭失败再次出现，随后同一 `alpha` 输入又执行 0 项。原先把飞书服务输出的二维码误当 TUI 证据，现已改为只认交互式终端客户端入口；飞书模型重审后只选命名 `dsh-lark`、SDK 主流程和额外 ACP/headless/Web，不再平白添加 TUI。`alpha` TUI 回执曾把执行任务数当兼容数，现需完整 `inspect({})` 的精确摘要与各层结果数才能 `conclude`，旧错误回执保留在归档。

一次飞书 `next` 启动因模型连续慢回合而出现 149 秒在线观察断点。broker 按启动编号把该轮所有报告和旧回执归档为 `unobserved`，同一模型会话重新实跑 14 项、终态巡检并准确结案，不能把失察轮次充作成功。Agent 运行器现新增独立于模型回合的确定性 `watch` 保底：插件真正启动后，在每轮模型前后及模型回合进行中每 10 秒读取本插件可信 broker 状态；观察调用限时已从 10 秒增至 35 秒，避免长仓库取证请求排队造成误停，启动前的证据补读不触发运行期 `watch`。观察失败仍停止结案；先红后绿的回归与协议测试已覆盖。新增保底机制还没有在真实模型失联的长中断场景实测，不能冒称它已经解决所有长中断。旧回执归档名称现在绑定启动编号、输入和回执摘要，多个旧回执不再互相覆盖；新启动前的本地 Agent 轮次文件也会归档。更早的轮次文件曾被覆盖，Codex 会话仍在，但本地轮次文件不能声称完整保留。

新增一轮真实 Cloudflare `next` Agent 复审，专门验证回合内保底：模型重新审阅并实际执行 Node 20/22 × 原生/Web 四项，运行期可信账本记录 23 次观察，最大间隔 9.981 秒。Node 20 两项因未注册失败，Node 22 两项通过。首次模型终态文字却把同版 Node 20 错写成 DSH `0.1.6-alpha.1`、Node 22 错写成作者基线，虽然精确账本的四项都只使用 DSH `0.1.5-rc.2`；这份错误回执已按精确编号和摘要归档。根因是旧 `inspect` 手段只给 Agent 结果，没有每项的 `dshVersion` 与 `nodeMajor`。现在完整 `inspect` 会给出这两个确定事实，`conclude` 还会拒绝账本里不存在的 DSH 版本；同一 Codex 会话在不伪造新执行的前提下重读四项并写出准确的单一 DSH 版本／两种 Node 归因。修复改变了执行器源码身份，确定性批次没有误用旧缓存，而是重新实跑四项；在新身份下再跑执行 0 项，三份账本和执行器证据字节摘要不变。这证明运行器保底在真实模型执行时确实参与在线观察，但仍不等于模拟过长时间完全失联。

目前仍未完成：远端凭证化 Actions 运行、100 插件公开 feed 的最新 DSH 全量重扫、飞书真人账号消息收发、部分浏览器精确 peer 核验。上述八例是本机真实 Agent MVP 的有界闭环，不等于整个社区兼容性证明。

网络故障的受控修复只覆盖直连、操作员预设的主代理和操作员预设的恢复代理，再配合有界重试；依赖本身不存在、供应链包有问题或作者文档缺失时，Agent 必须说明不可恢复原因并保留不完整覆盖，不能靠猜测绕过。浏览器精确 peer 版本和需要真实账号的集成测试同样仍是覆盖边界。

当前模型出口侧车若走上游代理，只支持无需凭证的 HTTP CONNECT 代理；目标插件的隔离执行代理配置另有独立校验。需要企业根 CA 的环境必须由操作员提供可信 PEM，再明确扩展受控出口，不能通过关闭 TLS 验证来“修复”下载或认证错误。
