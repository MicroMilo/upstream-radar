## 原始静态命中

这些是工具按规则给出的候选，不等于漏洞：

- 3 个仓库有安装阶段 `prepare`：`dsh-verification-receipt`、`@0xsline/dsh-spotlight`、`@nn12138/dsh-voice`。命令分别是构建命令或构建准备脚本；它们说明安装时会执行代码，需要审查，但没有证据表明它们是恶意代码。
- 17 个仓库没有可供当前工具锁定的依赖图。
- 5 个仓库共有 20 个浮动的 peer 依赖版本。
- `dsh-hdc-bridge` 有一个项目级 `.npmrc`，内容只是指向 npm 官方源；这是策略命中，不是恶意 registry。
- `anan-thermal-monitor` 包含 39 个 DLL/EXE 等原生文件。它还会在 Windows 上启动 PowerShell 桌宠进程，这是高信任能力和 provenance 审查点，不是依赖漏洞结论。

## 漏洞源结果与去伪

### 1. 发布物：没有确认的运行时依赖漏洞

30 个精确 npm 版本中，29 个完成了依赖图与 npm 漏洞审计，漏洞计数均为 0。另一个是 `anan-thermal-monitor@1.0.4`：Radar 自己的 tar 解析器不支持其中的 PAX size override，无法进入依赖审计；用系统 `tar` 验证后，发布物本身可以正常列出和读取，说明这是 Radar 解析能力缺口，不应把它写成“包损坏”或“恶意包”。

### 2. 两个看似严重的命中，其实是开发依赖

- `dsh-telemetry-redactor` 的源锁文件包含 `js-yaml@4.2.0`，OSV/GitHub Advisory 报告 [GHSA-5p4m-2wfm-xmqj](https://github.com/advisories/GHSA-5p4m-2wfm-xmqj) 和 [GHSA-52cp-r559-cp3m](https://github.com/advisories/GHSA-52cp-r559-cp3m)。但这条边是根包到 `devDependency`，不在其已发布 npm 包的运行依赖图中。
- `dsh-vision-web` 的源锁文件包含 `esbuild@0.24.2`，对应 [GHSA-67mh-4wv8-2f99](https://github.com/advisories/GHSA-67mh-4wv8-2f99)，修复版本为 `0.25.0`。这同样是 `devDependency`，而且该包的运行依赖为空，不能报告为安装后的 DSH 运行时漏洞。

另外，本轮原始扫描曾把已经达到修复版本 `js-yaml@4.3.1` 的一条边也报成受影响。
这不是上游插件问题，而是 Radar 对 GitHub Advisory Database 的
`first_patched_version` 边界处理错误。该误报已经在当前工作树修正：版本等于或高于
`first_patched_version` 时不再命中；新增回归测试同时验证 `2.9.0` 仍命中、`3.0.0`
不命中。联系作者前仍应使用修正后的版本重新扫描。

## 可以真正联系作者的问题

目前只有下面几类值得作为作者反馈候选，但还没有发 PR：

1. `dsh-composer-expand`：源码版本是 `0.1.2`，`package-lock.json` 根节点仍是 `0.1.0`。
   已用当前静态扫描在[维护者反馈草稿](dsh-composer-expand-lockfile-feedback.md)中复现。
2. `dsh-msg-hub`：源码版本是 `0.1.6`，锁文件根节点仍是 `0.1.1`。
3. `dsh-toolbox-web`：源码版本是 `0.1.5`，锁文件根节点仍是 `0.1.1`。

这三个问题不会自动证明存在漏洞，但会导致依赖图无法准确挂到当前插件版本上；对持续漏洞监控来说，它们是可复现、可解释、作者容易修复的质量问题。

## 方向判断

这 50 个样本暂时没有证明“我们能连续发现 DSH 插件的真实运行时漏洞”：确认数是 **0**。它证明了另一件事：当前工具能还原真实依赖图、接入两个漏洞源，也能识别出几个会让监控失真的输入问题（开发依赖混入、修复版本边界、嵌套插件目录、PAX tar 解析）。

因此本轮不应拿那两个开发依赖命中去给作者报漏洞，也不应现在批量发 PR。Upstream Radar 的作者反馈故事，至少要等到出现运行时依赖命中，或上述锁文件问题得到作者确认并愿意修复后才成立。
