## Repairable Feishu finding

The Feishu artifact was established as
`sha256:b6d7bcdd6fd25898f34c25b902d5905c88bf37b2b5a2c8e2c557f7e32f68c70f`.
DSH successfully invoked pnpm and pnpm materialized 73 packages, then exited 1:

```text
ERR_PNPM_IGNORED_BUILDS Ignored build scripts: protobufjs@7.6.5
Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
```

The checked dependency path is:

```text
dsh-feishu-bot
└── @larksuite/channel
    └── @larksuiteoapi/node-sdk
        └── protobufjs@7.6.5 (postinstall: node scripts/postinstall)
```

This is not evidence of malware, and it is not a DSH `rc.8` regression. The
same exact Feishu artifact failed at the same boundary under
[DSH `0.1.0-rc.7`](https://github.com/MicroMilo/upstream-radar/actions/runs/32462212520)
and [DSH `0.1.0-rc.8`](https://github.com/MicroMilo/upstream-radar/actions/runs/32462209585).
It is a clean-install contract problem: a new DSH profile cannot complete the
default non-interactive install until somebody explicitly decides whether
`protobufjs` may run its script.

The safe repair is not to disable pnpm's policy globally. DSH or the plugin
documentation should expose the exact approval step and explain why that script
is required; alternatively, the plugin can remove or replace the dependency
path if the script is unnecessary. Radar intentionally does not auto-approve
the build because that approval is the supply-chain trust decision being
measured.

## Evidence boundary

The compatible results prove this exact install/register/load path under the
recorded environment. The Feishu result proves the command failure and its
dependency-build cause. Same-container syscall traces remain best-effort and
the run does not exercise plugin business actions or external credentials.
